# 项目原生工具

> AuraBot 安装时幂等写入项目 SQLite 的内置工具。


## Task Agent

### FileSystem

FileSystem 是项目原生 MCP Server 提供给 Task Agent 的基础文件与命令执行 ToolGroup。
AuraBot 将 MCP Server 返回的 Tool `name` 原样暴露给 Agent，不生成别名。

#### 共同约定

- 所有 Tool 使用 MCP `tools/list` 返回的 `name`、`description`、`inputSchema` 和
  `outputSchema`；AuraBot 通过 OpenAI function tool 协议把 `name`、`description` 和
  `inputSchema` 提供给 Agent。
- 本节 `outputSchema` 只描述调用成功时 MCP `structuredContent` 的结构。调用失败时，
  MCP Server 必须返回 `isError = true`，并在文本内容中提供简短错误；可同时返回
  `{"error":{"code":"...","message":"..."}}` 形式的 `structuredContent`，但错误对象不受
  成功输出 Schema 约束。
- 相对路径以当前 Task 的工作目录为基准。绝对路径只能指向 Task 已授权的文件系统范围。
  服务端必须先规范化路径并解析符号链接，再检查权限；符号链接不能用于绕过授权范围。
- 路径中的 `~`、环境变量和 shell 表达式不自动展开。路径参数不是 Bash statement。
- 除 `bash` 外，文本读取和编辑统一使用 UTF-8。二进制文件、无法解码的文本文件返回
  Tool error。
- 文件大小使用 byte；行号和列号从 `1` 开始，`read_file.offset` 除外。
- 返回路径使用规范化绝对路径。目录项和搜索结果按路径、行号、列号稳定排序。
- 文件系统 Tool 不跟随目录符号链接递归遍历。

#### `edit_file`

**MCP Server 返回的 Tool 名称**

```text
edit_file
```

**Tool 功能描述**

```text
原子编辑一个已存在的 UTF-8 文本文件。按 edits 顺序执行精确文本替换；默认要求 old_text 在当时内容中恰好出现一次，replace_all=true 时替换全部出现位置。expected_sha256 可校验 read_file 返回的文件版本，避免覆盖并发修改。任一校验或替换失败时不写入任何内容。
```

`edit_file` 采用精确替换，而非整文件覆盖：

- `edits` 在内存中的中间内容上依次执行，全部成功后才原子替换原文件。
- `replace_all` 省略或为 `false` 时，`old_text` 必须恰好出现一次；出现 `0` 次或多次均
  返回错误。
- `replace_all = true` 时，`old_text` 必须至少出现一次。
- `old_text` 可以为空字符串，但只允许 `edits` 仅有这一项、目标文件为空；
  `new_text` 将成为文件全部内容。此规则用于写入 `create_file` 创建的空文件。
- `new_text` 可以为空字符串，表示删除匹配内容。
- 提供 `expected_sha256` 时，服务端必须在修改前验证当前文件哈希；不一致时返回冲突，
  Agent 应重新调用 `read_file`，不能盲目重试旧编辑。
- 写入时保留原文件权限；不允许通过符号链接编辑授权范围外文件。

**MCP Tool 输入 JSON Schema**

```json
{
  "type": "object",
  "properties": {
    "path": {
      "type": "string",
      "minLength": 1,
      "description": "要编辑的已存在 UTF-8 文本文件路径。"
    },
    "edits": {
      "type": "array",
      "minItems": 1,
      "maxItems": 100,
      "description": "按声明顺序执行的精确文本替换列表。",
      "items": {
        "type": "object",
        "properties": {
          "old_text": {
            "type": "string",
            "description": "必须在当前中间内容中匹配的原始文本。"
          },
          "new_text": {
            "type": "string",
            "description": "用于替换 old_text 的新文本；空字符串表示删除。"
          },
          "replace_all": {
            "type": "boolean",
            "default": false,
            "description": "是否替换 old_text 的全部出现位置；省略时为 false。"
          }
        },
        "required": ["old_text", "new_text"],
        "additionalProperties": false
      }
    },
    "expected_sha256": {
      "type": "string",
      "pattern": "^[0-9a-f]{64}$",
      "description": "可选的修改前文件 SHA-256，通常取自最近一次 read_file。"
    }
  },
  "required": ["path", "edits"],
  "additionalProperties": false
}
```

**MCP Tool 输出 JSON Schema**

```json
{
  "type": "object",
  "properties": {
    "path": {
      "type": "string",
      "description": "文件的规范化绝对路径。"

      "type": "boolean",
```

#### `bash`

**MCP Server 返回的 Tool 名称**

```text
bash
```

**Tool 功能描述**

```text
在 PATH 指定的 Task 沙箱目录中通过非交互式 Bash 执行一段 statement，返回 stdout、stderr 和退出状态。PATH 可以是 Task 工作目录相对路径或沙箱内绝对路径，由 FileSystemAdaptor 规范化为绝对路径。每次调用使用独立 shell，不保留 cd、变量、alias 或 shell option。命令受 Task sandbox、文件系统授权、网络策略、审批策略、固定超时和输出上限约束；超时或输出截断会在结果中明确标记。
```

命令成功启动后，即使退出码非 `0` 或执行超时，也返回符合下述 `outputSchema` 的结果；
策略拒绝、Bash 无法启动等未执行情况返回 Tool error。

### Plan

Plan 是 Plan-and-Solve Task Agent 使用的项目原生 ToolGroup。它只负责维护当前
Task 的执行计划，不执行计划中的业务动作。

Plan 的唯一 runtime owner 是 `PlanAndSolveHarness`，不是 `Task`。
`Task` 始终是 ReAct、Plan-and-Solve 和未来 Harness 共用的独立通用实体，不包含
`plan`、`goal` 或其他 Plan 专属字段。直接读取 Plan 时得到的是 Harness 持有的
不可变 `PlanSnapshot`；所有状态转换必须通过 Harness 的 Plan 方法完成。

#### 共同约定

- 本 ToolGroup 只包含 `create_plan`、`read_plan`、`update_plan` 和
  `plan_step_complete` 四个 Tool。
- `task_name` 是系统路由上下文，不是 Tool 业务参数。它不得出现在任何 Tool 的
  `inputSchema`、`outputSchema`、LLM 可见描述或成功结果中。
- OpenAI 原生 Tool Call 解析并完成权限解析后，`PlanContextAdaptor` 必须在进入
  `ToolCallGateway` 前，把当前 Task 的唯一名称写入标准 MCP `tools/call`
  请求的 `_meta`：

```json
{
  "aurabot": {
    "task_name": "当前 Task 的唯一名称"
  }
}
```

- Adaptor 注入 `_meta` 时不得修改 LLM 生成的业务 `arguments`。模型生成的
  `task_name`、`_meta` 或 backend URL 都不可信，也不得用于 Task 路由。
- MCP Server 必须从请求上下文读取 `_meta.aurabot.task_name`。字段缺失、类型错误、
  空字符串或首尾含空白时返回 `invalid_task_context` Tool error，且不得向 backend
  发起请求。
- Backend 与 MCP Server 是两个独立进程。Plan Tool 在 MCP Server 中完成参数校验后，
  分别向 backend 发起以下本机 HTTP 请求：

    - `create_plan` -> `POST http://127.0.0.1:6401/tool/plan/create`
    - `read_plan` -> `POST http://127.0.0.1:6401/tool/plan/read`
    - `update_plan` -> `POST http://127.0.0.1:6401/tool/plan/update`
    - `plan_step_complete` ->
      `POST http://127.0.0.1:6401/tool/plan/step/complete`

- MCP Server 发给 backend 的内部请求体由 Adaptor 注入的 `task_name` 和经过 Schema
  校验的 Tool arguments 组成。backend URL 固定来自项目配置，不接受 Tool arguments
  或 `_meta` 覆盖。
- Backend 的四个内部 HTTP Body 使用扁平结构，不嵌套 `arguments`：

    - create：`task_name + goal + steps`
    - read：`task_name`
    - update：`task_name + goal + steps`
    - complete：`task_name + step_id + completion_summary`

- Backend 的 `TaskManager` 根据唯一 `task_name` 定位完整 Harness runtime，再确认其为
  `PlanAndSolveHarness`。Plan 不从 Task 字段读取，也不复制到路由记录中。
- 一个 `PlanAndSolveHarness` 最多有一个 Plan。一个 Plan 包含一个目标和 `1` 至
  `30` 个有序步骤。
- Step `id` 在当前 Plan 内必须唯一，并在该 Step 的整个生命周期内保持稳定。JSON
  Schema 的 `uniqueItems` 只能拒绝完全相同的对象，backend 还必须单独校验 `id`
  唯一性。
- Step 只有 `pending` 和 `completed` 两种状态。Plan 创建时全部为 `pending`；
  `plan_step_complete` 是唯一允许把 Step 改为 `completed` 的 Tool。
- 已完成 Step 始终构成 Plan 的有序前缀；第一个 `pending` Step 是
  `current_step_id`。不允许跳过当前 Step 完成后续 Step。
- `update_plan` 不能直接提交 `status` 或 `completion_summary`。它必须保留已完成前缀
  的 ID、顺序和内容；只能修改、删除、重排未完成后缀，或在后缀中增加新 Step。
- `update_plan` 不得删除全部剩余的 `pending` Step。最后一个 pending Step 只能由
  `plan_step_complete` 转为 completed；试图把更新结果缩减为仅有已完成前缀时返回
  `invalid_plan`。
- Plan 已完整结束后，`create_plan` 和 `update_plan` 返回
  `invalid_task_state`。在 Task 进入终态前，`read_plan` 以及使用相同摘要重放已完成
  Step 仍可使用。
- `read_plan` 是唯一返回完整 PlanSnapshot 的 Tool。`create_plan`、`update_plan` 和
  `plan_step_complete` 只返回推动下一轮推理所需的最小状态转换回执，不重复返回
  完整 Plan。
- 写 Tool 的回执表示请求所要求的目标状态已经成立，不区分首次写入和幂等重放，
  也不增加 `replayed`、`changed` 等辅助字段。MCP Server 与 backend 可以在内部
  交换并校验完整 PlanSnapshot，但不得把内部响应原样暴露给 LLM。
- 所有成功输出都不包含 `task_name`。
- Tool 参数不匹配 `inputSchema` 时返回 `invalid_arguments`。业务状态冲突和 backend
  通信错误使用本节定义的稳定错误码，不向 LLM 泄露 backend 响应正文、堆栈、端口外
  的内部地址或其他 Task 信息。

  `completed`，并把 `current_step_id` 推进到下一个 pending Step；没有 pending
  Step 时返回 `next_step_id = null` 和 `is_complete = true`。

  幂等调用；`next_step_id` 必须返回调用时最新的第一个 pending Step，而不是保存并
  重放该 Step 首次完成时的历史回执，不暴露该调用是否发生了写入。
- 已完成 Step 收到不同 `completion_summary` 时返回
  `step_already_completed`，不得改写历史完成记录。

#### Plan Tool error code

除共同的 `invalid_arguments` 外，Plan Tool 使用以下稳定错误码：

| code | 含义 |
| --- | --- |
| `invalid_task_context` | MCP `_meta` 缺少合法的 `aurabot.task_name`。 |
| `task_not_found` | Backend 中不存在该名称对应的运行时 Task。 |
| `invalid_task_type` | 目标 Task 不是 Plan-and-Solve Task。 |
| `invalid_task_state` | Task 已完成、失败或被中断，当前状态不允许 Plan 操作。 |
| `plan_already_exists` | `create_plan` 试图用不同内容覆盖已有 Plan。 |
| `plan_not_found` | 需要现有 Plan 的操作在 Plan 创建前执行。 |
| `invalid_plan` | Step ID 重复或 Plan 违反 Schema 之外的跨字段约束。 |
| `completed_step_immutable` | `update_plan` 试图修改已完成 Step 前缀。 |
| `step_not_found` | `plan_step_complete.step_id` 不存在。 |
| `step_not_current` | 试图跳过当前 Step 完成其他 pending Step。 |
| `step_already_completed` | 试图用不同摘要改写已完成 Step。 |
| `backend_unavailable` | MCP Server 无法连接 backend。 |
| `backend_timeout` | backend Plan 请求超时。 |
| `backend_protocol_error` | backend 返回了无法验证的状态码或响应体。 |
| `internal_error` | MCP Server 内部出现未预期错误。 |

错误结果必须使用 `isError = true`。文本内容只提供简短、可行动说明；
`structuredContent` 可以使用
`{"error":{"code":"...","message":"..."}}`，但不得包含 `task_name`、backend
原始响应正文或异常堆栈。
