## 2. 产品定义

### 2.1 一句话定义

AuraBot 是一个运行在桌面端的、以“高活人感聊天陪伴”为第一优先级，同时具备任务代理与轻量助手能力的 AI 伴侣型产品。

### 2.2 核心定位

AuraBot 不是一个纯工具型助手，也不是一个只有人设包装的闲聊机器人。它的目标是：

- 像一个“真正会聊天、会记人、会找话题、会做事”的长期陪伴对象。
- 在保持陪伴感的前提下，具备把任务委派给下层能力或外部工具执行的能力。
- 让用户在和它互动时，尽量不产生“我正在和一个严格按指令工作的机器人说话”的割裂感。

### 2.3 方向判断

围绕产品方向，讨论中实际出现了三种可能路径：

| 路径 | 描述 | 优点 | 问题 |
| --- | --- | --- | --- |
| 助手优先 | 把产品做成超级助手，聊天只是入口 | 工具价值明确，任务闭环清晰 | 陪伴感、沉浸感和活人感会弱 |
| 陪伴优先 | 把产品做成强情绪价值的聊天伴侣，任务能力弱化 | 更容易形成差异化和长期关系感 | 工具价值不足，实用性偏弱 |
| 陪伴优先的混合型 | 以聊天陪伴体验为主，兼具任务代理能力 | 既有情感价值，也能形成日常使用频率 | 设计复杂度最高，需要清晰边界 |

推荐路线：`陪伴优先的混合型`。

原因如下：

- 讨论中最强烈、最反复被强调的痛点不是“工具不够多”，而是“现有产品太像机器人，不像人”。
- 任务助手能力是必要增益，但不是核心差异点。
- 如果产品先把“像人聊天”这件事做扎实，再叠加任务能力，整体竞争力会高于“又一个万能助手”。

## 3. 背景与问题陈述

当前市面上的陪伴型或助手型 AI 存在以下共性问题：

1. 记忆机制偏弱，难以形成真实、长期、可联想的人际感。
2. 对话触发逻辑机械，经常以单条消息或固定超时为单位触发回复，破坏聊天沉浸感。
3. 话题延展方式过于模板化，经常出现“要不要我再教你一下”“要不要我给你介绍几个方法”这类明显的 AI 套话。
4. 人格更多停留在提示词表层，无法真正影响主动找话题、插话时机、表达习惯和关系感。
5. 助手能力与聊天能力往往没有统一设计，要么像纯工具，要么像纯玩具。

AuraBot 需要解决的不是单一功能点，而是一整套“陪伴感生成机制”：

- 记忆如何存
- 记忆如何取
- 什么时候该说话
- 什么时候该等
- 怎么找到新话题
- 如何既像人一样聊天，又能像助手一样做事

## 4. 产品目标

### 4.1 总目标

打造一个能长期陪伴用户、具有高活人感、高可持续对话能力，并能完成部分实际任务的桌面端 AI 伴侣。

### 4.2 具体目标

1. 让用户可以像和真实朋友聊天一样与 AuraBot 互动，而不是被迫迁就机器人式对话规则。
2. 让 AuraBot 具备比现有陪伴机器人更强的记忆连贯性、联想能力和事件跟踪能力。
3. 让 AuraBot 可以在用户需要时承担任务代理角色，例如调用工具、执行简单工作流、生成周期性输出。
4. 让 AuraBot 支持多角色档案，以便同一台设备上养成多个不同人格/记忆体。
5. 采用分阶段交付方式，先验证核心聊天内核，再逐步扩展任务和外部接入能力。

### 4.3 成功标准

若产品成功，用户主观上应产生以下感受：

- “它记得我，而且记得不是死记硬背。”
- “它说话不机械，不会每次都用同一种 AI 话术。”
- “我不用为了配合它而改变自己的聊天方式。”
- “它不是只会陪聊，也真的能替我做点事。”
- “当它在做任务时，我依然能和它保持主对话。”

## 5. 非目标

以下内容不作为第一阶段必须完成的目标：

1. 一上来就接入所有游戏、平台或复杂外部生态。
2. 多角色之间的互相协作、互相对话或复杂联动。
3. 无限层级的任务递归调用。
4. 纯靠提示词就解决全部活人感问题。
5. 在没有可交付原型验证前，直接把全量愿景一次性端到端做完。

## 6. 目标用户与典型使用场景

### 6.1 目标用户

#### 用户画像 A：高频聊天陪伴用户

- 希望拥有一个长期陪聊对象
- 在意“像不像真人”和“有没有情绪价值”
- 讨厌机械式回复、被动式延展和低质量记忆

#### 用户画像 B：桌面端重度使用者

- 长时间在电脑前工作或娱乐
- 希望一个常驻桌面的角色型 AI 陪伴自己
- 既需要聊天，也希望对方能顺手帮自己做些小事

#### 用户画像 C：轻任务委派用户

- 不一定把 AuraBot 当生产力主工具
- 但希望它能做定时提醒、简报汇总、信息搜集、简单执行
- 更希望它“像一个会去帮你办事的人”，而不是“另一个复杂 IDE”

### 6.2 核心使用场景

1. 用户以碎片化、多条连续消息的方式聊天，AuraBot 需要判断何时自然接话，而不是抢答。
2. 用户在日常聊天中暴露偏好、事件和关系线索，AuraBot 需要在未来对话中自然调用。
3. 用户希望 AuraBot 主动找到新话题，而不是永远被动顺着用户话题说下去。
4. 用户交给 AuraBot 一个任务后，仍然可以继续与其聊天，并在必要时查询或修改任务。
5. 用户希望 AuraBot 在特定时间主动完成提醒、推送或周期性任务。
6. 用户在同一设备上创建多个不同人格的 AuraBot，并在它们之间切换。

## 7. 产品原则

### 7.1 聊天优先

AuraBot 首先要是一个优秀的聊天陪伴体，其次才是具备任务能力的助手。任何功能设计都不能明显破坏聊天的自然感。

### 7.2 活人感优先于功能堆砌

真正的差异化不在于支持多少工具，而在于说话像不像人、记人像不像人、等人像不像人。

### 7.3 结构创新聚焦在核心差异点

以下能力不是核心创新点，可以尽量复用成熟方案：

- MCP 接入
- Skill 机制
- QQ/微信等渠道接入
- 常规工具调用协议

真正需要自己拍板和打磨的是：

- 记忆结构
- 对话触发协议
- 会话与任务管理策略
- 主线程与任务线程的体验边界

### 7.4 分阶段交付

必须保留中间可交付成果。优先把聊天、记忆、触发三者跑通并验证，再决定如何扩大范围。

## 9. 核心功能需求

### 9.1 人格与 Soul 系统

#### 需求目标

AuraBot 需要具备稳定、可持续的人格基底，而不是仅靠单次提示词临时扮演角色。

#### 功能要求

1. 每个 Profile 必须拥有独立的 `Soul` 配置。
2. `Soul` 至少定义以下内容：
   - 人格底色
   - 表达风格
   - 对用户的关系定位
   - 可接受与不可接受的互动边界
   - 话题偏好
   - 主动发起话题的风格倾向
3. Soul 只负责“人格底稿”，不能被视为活人感的唯一来源。
4. 系统必须允许行为层策略覆盖“只有提示词、没有机制”的局限。

#### 设计结论

- `Soul` 是必要但不充分条件。
- 主动找话题、对话时机判断、说话节奏等关键体验，不能只依赖 Soul 文本描述。

### 9.2 记忆系统

#### 需求目标

AuraBot 的记忆系统既要有检索效率，也要有“像人一样联想”的能力，不能只做成简单的列表、堆叠摘要或固定树状目录。

#### 推荐方向

采用“`分层摘要 + 图状联想`”的混合记忆结构。

这一路线吸收两类思路：

1. `分层摘要`：借鉴分层记忆方案，通过高层概述降低 Token 成本，提升检索效率。
2. `图状联想`：通过节点与边表达跨主题、跨类别的联想关系，增强活人感与话题跳转能力。

#### 记忆类型

至少划分两大类：

1. `时间驱动记忆`
   - 典型例子：下周去看演唱会、今晚有考试、明天交作业
   - 特征：与时间、状态推进、后续追问强相关
   - 生命周期：创建 -> 待跟进 -> 已完成 -> 沉淀为普通记忆
2. `非时间驱动记忆`
   - 典型例子：喜欢吃火锅、讨厌跑步、偏爱某类游戏
   - 特征：更稳定，主要用于长期个性化互动

#### 记忆写入要求

1. 不能简单按固定条数机械总结记忆。
2. 系统应支持基于“对话段落/话题段落结束”的记忆写入机制。
3. 写入时应判断：
   - 是否值得写入
   - 写入哪类记忆
   - 重要度
   - 与已有节点的关系
4. 需要存储产生时间、最近更新时间、重要度、关联边等信息。
5. 必须防止同一事实被无约束地重复写入多个位置。

#### 记忆读取要求

1. 支持先读概述，再决定是否展开具体记忆。
2. 支持根据当前对话主题进行联想型召回，而不只是关键词命中。
3. 对近期记忆需要有显式偏权机制，例如突出近若干小时内的记忆。
4. 对时间驱动记忆，应支持时间到点前后触发追问或关怀。

#### 风险

图状记忆的读写协议设计难度高，尤其在以下方面：

- 如何避免重复节点泛滥
- 如何定义边类型与边权重
- 如何控制检索成本
- 如何解释“联想跳转”而不让回复显得离题

### 9.3 对话触发系统

#### 需求目标

用户不应被迫以“机器人友好型输入方式”说话。AuraBot 需要尽可能判断用户是否真的说完，避免抢话、打断或过早输出。

#### 核心结论

固定 `timeout` 只能作为保底机制，不能作为首选方案。

#### 功能要求

1. 系统必须具备“是否该开口”的独立判断机制。
2. 推荐引入一个轻量级判断单元，用于处理以下问题：
   - 用户是否说完
   - 当前是否应该回复
   - 当前输入是闲聊还是任务请求
   - 当前对话段是否结束，是否可以触发记忆整理
3. 主回复模型不应承担所有低价值判断任务，以降低：
   - 成本
   - 上下文污染
   - 架构耦合
4. 系统应支持打断机制：
   - 若用户在 AuraBot 生成回复过程中补充了新内容，应允许中止或重判当前回复
5. 回复投放建议通过显式“发送动作”完成，而不是默认所有生成都自动出现在用户面前。

#### 体验要求

1. 用户连续发多条短消息时，AuraBot 应尽量等待完整语义段落形成后再回。
2. 用户打字慢、删改字、组织语句时，不应因固定时延过短而频繁被打断。
3. 用户不应该因为担心窗口期结束而产生明显紧迫感。

### 9.4 话题管理与活人感增强

#### 需求目标

AuraBot 需要能主动找话题，并且找话题的方式不能高度模板化。

#### 功能要求

1. 不能只顺着用户话题被动延展。
2. 必须支持在适当时机主动开启新话题。
3. 主动话题应优先来源于：
   - 近期事件记忆
   - 长期兴趣偏好
   - 当前情境
   - 关系上下文
4. 禁止默认使用统一、重复的 AI 套话模板。
5. 在聊天模式下，AuraBot 应允许表达不同意见，而不是一味迎合用户。

#### 设计要点

“像人一样找话题”不能被简化成一条提示词，而需要依赖以下几个系统联动：

- Soul 决定人格底色
- 记忆系统提供材料
- 对话触发系统决定是否插话
- 生成系统决定如何自然地说出来

### 9.5 聊天与任务的输入分类

#### 需求目标

AuraBot 需要判断用户当前是在聊天，还是在委派任务，因为这两类输入对应完全不同的处理路径。

#### 功能要求

1. 系统必须具备 `聊天型输入 / 任务型输入` 分类能力。
2. 分类单元可与“是否开口”判断单元合并。
3. 若判定为任务型输入，应触发任务处理流程，而不是直接在聊天上下文里硬做任务。
4. 若判定为聊天型输入，应优先留在主聊天会话中响应。

### 9.6 任务代理能力

#### 需求目标

AuraBot 的任务能力定位不是替代专业开发工具，而是像“一个会自己去调用工具帮你办事的人”。

#### 功能要求

1. AuraBot 可以把某些任务委派给外部工具、Skill、MCP 或专门的执行代理。
2. 典型任务包括但不限于：
   - 搜集资料
   - 做表格
   - 写周报
   - 调用 Coding Agent 执行简单开发任务
   - 定时发送信息
3. 任务执行上下文必须与主聊天上下文分离，防止上下文污染。
4. 任务结果需要回流到主对话可感知范围内。

#### 边界

1. AuraBot 不等于 Claude Code / Codex 本体。
2. AuraBot 更像“主代理”，专业工具是其下游能力。

### 9.7 会话、线程与任务树管理

#### 需求目标

用户与 AuraBot 的长期关系必须有唯一主聊天上下文；与此同时，任务执行需要可分离、可管理、可回流。

#### 推荐结构

采用“`单主聊天线程 + 若干任务子线程`”的树状结构。

#### 结构要求

1. 主聊天线程全局唯一。
2. 用户与 AuraBot 的长期关系、主要对话、主要记忆都以主聊天线程为中心。
3. 每个任务应在独立任务线程中执行。
4. 任务线程允许开出下一层子任务，但必须限制最大层数，推荐不超过 3 层。
5. 禁止无限递归开子任务，避免失控和资源爆炸。

#### 权限与优先级要求

1. 主聊天线程优先级高于任务线程。
2. 当主聊天线程与任务线程同时竞争记忆或响应资源时，应优先保证用户聊天体验。
3. 主聊天线程应具备对任务线程的管理权限，至少包括：
   - 查询状态
   - 打断任务
   - 修改任务方向
   - 接收阶段性结果

#### 当前未完全拍板的问题

1. 用户是否可以直接进入某个任务子线程查看详细过程。
2. 任务进度查询是统一在主线程完成，还是允许独立查看任务会话。
3. 多任务同时运行时，记忆写入冲突如何仲裁。

### 9.8 多 Profile

#### 需求目标

用户可以在同一设备上维护多个独立的人格体，每个角色拥有自己的 Soul、记忆和状态。

#### 功能要求

1. 支持创建多个 Profile。
2. 每个 Profile 拥有独立：
   - Soul
   - 记忆库
   - 任务上下文
   - 配置文件
3. 用户可以切换当前活跃 Profile。
4. 第一阶段不要求不同 Profile 之间互相对话或协作。

### 9.9 定时任务与后台主动行为

#### 需求目标

AuraBot 不应只在被动接收到消息时工作，还应在用户授权下执行定时、周期性或条件触发行为。

#### 功能要求

1. 支持用户定义计划任务，例如：
   - 每晚 8 点发送 GitHub 周报
   - 每天 9:30 盯盘
   - 定期提醒某件事
2. 定时任务应走独立任务调度路径。
3. 定时任务触发后，结果应回流到用户可见入口。
4. 与时间驱动记忆联动时，可以形成“事件追问”和“提醒关怀”。

### 9.10 渠道与接入

#### 初始结论

外部接入不是核心创新点，应优先复用成熟方案。

#### 需求范围

1. 产品本体需有桌面端主入口。
2. 后续可接入 QQ、微信等聊天渠道。
3. Live2D/桌宠式展示形态是桌面端默认交互壳层：平时只常驻一个小人，悬浮后显示拖拽、语音和控制台按钮，需要完整对话时再打开控制台视窗。
4. 传统聊天窗口只能作为按需打开的控制台视窗，不能成为第一主视觉；任务控制不能做成独立按钮面板，必须通过主聊天线程查询、打断、修改和启动。
5. 复杂游戏接入放在更后阶段，不作为第一阶段交付前提。

### 9.11 桌面端交互壳层

#### 需求目标

AuraBot 既然是桌面端产品，就不能只有“能力内核”，还必须提供一套能承载陪伴感与助手能力的桌面交互外壳。

#### P0 交互要求

1. 必须提供桌面小人常驻入口，默认窗口应是透明、轻量、桌宠式的 Live2D 小人。
2. 用户悬浮小人后，必须能通过控制台按钮打开控制台视窗作为完整主聊天入口。
3. 控制台视窗至少包含：
   - 消息流
   - 输入区
   - AuraBot 当前状态展示，例如思考中、等待中、执行任务中
4. 用户必须能明确感知 AuraBot 当前是在聊天、思考，还是在后台处理任务。
5. 需要有基础通知或提示机制，用于承接：
   - 主动发起的话题
   - 定时任务结果
   - 任务完成提醒
6. 任务查询、打断、修改、启动只能经由控制台里的主聊天线程完成，不提供独立任务控制按钮。

#### P1 交互要求

1. 在控制台中提供轻量任务状态展示，允许用户查看当前有哪些任务在执行。
2. 提供 Profile 切换入口。
3. 提供基本设置入口，至少包含：
   - 当前 Profile
   - 定时任务配置
   - 外部渠道接入状态
4. Live2D/桌宠形态必须承载主体验；控制台是对话和调试展开面，不能退化成一个长期常驻的传统仪表盘。

## 10. 关键体验流程

### 10.1 自然聊天流程

1. 用户发送一条或多条碎片化消息。
2. 轻量判断单元持续判断用户是否说完。
3. 若尚未说完，则暂缓主回复。
4. 若已形成完整语义段，则决定是否回复。
5. 回复前拉取相关记忆与当前上下文。
6. 生成自然回复并投放。
7. 在适当时机判断该段对话是否结束，决定是否整理记忆。

### 10.2 任务委派流程

1. 用户在主聊天线程中提出任务。
2. 分类单元识别为任务型输入。
3. 系统创建任务线程并分配执行代理。
4. 任务线程调用工具、Skill 或外部代理完成工作。
5. 主线程可接收任务状态更新或最终结果。
6. 用户如改变想法，可在主线程中中断或修改任务。

### 10.3 时间驱动记忆流程

1. 用户提到未来某个事件。
2. 系统将其写入时间驱动记忆。
3. 到达关键时间点前后，系统根据上下文决定是否主动提起。
4. 事件结束后，根据结果沉淀为普通长期记忆或标记完成。

## 11. 数据与对象模型建议

为保证后续实现清晰，建议系统中至少显式建模以下对象：

| 对象 | 说明 |
| --- | --- |
| Profile | 单个人格体的完整容器 |
| Soul | 人格、语气、偏好、边界等设定 |
| MemoryNode | 一条记忆节点 |
| MemoryEdge | 两条记忆之间的关联 |
| Session | 一次会话上下文，可能是聊天或任务 |
| Task | 可执行任务实体 |
| Schedule | 定时任务配置 |
| ToolBinding | 可调用工具或 Skill 映射 |
| EventLog | 运行日志、调度轨迹、打断记录 |

## 12. 非功能性需求

### 12.1 延迟

1. 聊天模式下，应优先保证用户可感知的响应自然度。
2. “是否开口”的轻量判断必须足够快，不能显著拖慢整体体验。

### 12.2 成本

1. 低价值判断不应长期占用高成本主模型。
2. 记忆检索必须有控 Token 机制。

### 12.3 一致性

1. 多任务并发时，记忆库读写必须有明确队列或锁策略。
2. 任务状态必须可追踪，不能出现主线程不知道子任务在做什么的黑箱状态。

### 12.4 可扩展性

1. 工具调用、Skill 接入、外部渠道接入应模块化。
2. 核心内核不应与单一渠道耦合。

### 12.5 可验证性

1. 每个阶段都必须有可运行、可观察、可评估的中间成果。
2. 不能只写概念，不做原型验证。

## 13. 分阶段交付建议

### 阶段 1：聊天内核验证版

目标：验证最核心的差异化假设是否成立，并确认 Live2D/桌宠式壳层能承载聊天陪伴的主体验。

范围：

- Soul 基础能力
- 记忆系统第一版
- 对话触发第一版
- 基础回复生成
- 基础话题管理
- Live2D/桌宠式桌面入口，默认只显示小人；悬浮小人后显示轻量控制，控制台视窗承载聊天输入、消息流、状态与任务概览

验证重点：

- 图状/混合记忆是否真能带来更自然的联想
- 触发机制是否明显优于固定超时
- 对话是否减少“机器人感”

### 阶段 2：聊天 + 任务一体版

范围：

- 聊天/任务分类
- 任务线程
- 主线程查询/打断/修改任务
- 简单工具接入
- 基础定时任务

验证重点：

- 主聊天体验是否会被任务能力拖垮
- 任务线程与记忆写入是否冲突
- 用户是否真正需要在聊天中管理任务

### 阶段 3：多 Profile 与渠道扩展版

范围：

- 多 Profile 管理
- QQ/微信等渠道接入
- 更稳定的后台调度

### 阶段 4：复杂外部生态接入

范围：

- 游戏接入
- 更复杂的自动化和任务编排
- 更高阶的主动行为系统

## 14. 验证指标建议

### 14.1 聊天体验指标

1. 用户主观“像人程度”评分
2. 被抢话/被打断不适感评分
3. 主动发起话题的自然度评分
4. 模板化话术重复率

### 14.2 记忆指标

1. 记忆召回命中率
2. 联想跳转有效率
3. 时间驱动事件跟进成功率
4. 重复记忆写入率

### 14.3 任务指标

1. 任务识别准确率
2. 任务执行完成率
3. 主线程查询任务状态成功率
4. 打断/修改任务成功率

## 15. 风险与待验证项

以下内容在讨论中被明确提到，但尚不足以直接视为完全定板，需要在原型阶段重点验证：

1. 图状记忆的实际收益是否足够大，是否值得其实现复杂度。
2. “对话段结束判断”能否稳定替代固定条数总结。
3. 主线程是否必须具备对子线程的完全可视、可控能力。
4. 用户到底更想要“超级老婆”还是“超级助手”，以及两者最优平衡点。
5. 多线程任务和记忆写入之间的竞态条件如何处理。
6. 任务线程是否应该允许用户直接进入查看过程；当前 MVP 先不开放任务子线程视窗，统一通过主线程对话查询。
7. 主动找话题能否真正做到多样、自然，而非换皮模板。

## 16. 本次讨论形成的结论摘要

### 已形成较强共识

1. 产品方向应为“陪伴优先的聊天型 AI，兼具助手能力”。
2. 第一阶段先做聊天、记忆、触发，不先做全量生态接入。
3. 记忆系统需要突破常规列表式或纯树式设计，至少要保留联想能力。
4. 固定超时不是理想的聊天触发方式，只能作为保底。
5. 聊天与任务必须分路径处理。
6. 需要中间可交付成果，不能一把梭做完整工程。

### 仍需实验验证

1. 图状记忆的具体数据结构与读写协议
2. 主线程和任务线程的精确权限模型
3. 任务进度查询在主聊天线程中的具体表达形态
4. 子任务最大层数与调度策略
5. 外部渠道与桌面本体的优先级排序

## 17. 推荐的下一步

如果把这份 PRD 作为后续实现的输入，推荐下一步不是直接做全量系统，而是先进入“聊天内核验证版”的方案拆解，最先验证三件事：

1. 混合记忆结构是否可行。
2. 非固定超时的触发机制是否显著提升聊天体验。
3. 聊天主线程与任务子线程的基本边界能否跑通。

只有这三件事验证成立，AuraBot 才有必要继续往多 Profile、复杂任务与游戏接入扩展。
