AuraBot 任务系统现在怎么运转

这份 HTML 用更直观的方式说明当前任务机制。重点不是把所有代码细节摊开，而是让团队快速看懂：任务从哪里来、怎么启动、状态如何可信、结果怎么回流，以及下一步应该优化哪里。

当前结论

现在的任务系统已经不是简单的待办列表，而是一套聊天入口、后台执行、事件记录、产物回流和界面展示共同组成的轻量任务协调器。

入口 主聊天负责识别任务

用户直接在聊天里说“帮我写一份周报”，gate 会判断是普通聊天、任务，还是任务控制。

执行 后台启动，不阻塞聊天

任务启动先抢占 queued -> running，成功后交给后台执行器，聊天立即返回处理中状态。

结果 产物优先来自产物表

文件结果写入 task_artifacts，附件展示和打开文件优先信这个表，事件推断只兜底。

可观测 控制台可以看详情

任务便签新增详情入口，可看状态、执行器、目录、安全模式、时间线、产物和最近错误。

一句话版

现在的任务系统更像一个“小型后台任务协调器”：聊天负责发起和控制，主进程负责抢占和执行，事件负责记录过程，产物表负责可信结果，控制台负责展示和排障。

端到端流程

从用户一句话，到任务完成回到主聊天，大致经过下面这条路径。

1 用户输入

主聊天或桌宠输入收到自然语言请求。

2 Gate 判断

识别为 chat、task 或 task_control。

3 创建任务

写入 tasks，创建任务会话，初始状态为 queued。

4 原子抢占

后台启动前先执行 queued -> running 条件更新。

5 执行器运行

确定性 runner 或 Codex / Claude Code / Hermes CLI 子进程执行。

6 事件与产物

进度写入 task_events，文件结果写入 task_artifacts。

7 回流界面

广播任务变化，完成后发聊天消息、附件和桌宠活动。

状态机制

任务状态已经从“各处约定”收口到 taskState.ts，后台启动也必须通过仓储层的条件状态转换。

queued 待开始

可以被启动。后台启动会抢占到 running。

running 执行中

正在处理，进度会通过 task:changed 广播。

waiting 等待中

暂时保留为等待外部动作或取消过程的活跃状态。

completed 完成

会触发结果回流，附件优先来自产物表。

failed 失败

详情面板显示最近错误，后续可扩展重试。

interrupted 已停下

用户取消或打断后的终态，可删除或后续扩展继续。

状态判断 当前规则 作用
isActiveTask queued、running、waiting 用于取消、便签展示和活跃任务判断。
isSettledTask completed、failed、interrupted 用于删除、终态消息和结果展示。
isRunnableTask 仅 queued 确保只有待开始任务能被启动。
transitionStatus 条件更新并校验合法转移 防止重复启动和非法状态跳转。

核心数据模型

当前任务系统主要依赖三类数据：任务本体、任务事件、任务产物。

tasks 任务本体
  • title：用户可见标题，也是执行提示词核心。
  • kind：result_output 或 time_reminder。
  • status：当前状态。
  • latestProgress：界面和状态回复使用的最近进展。
  • dueAt：提醒任务的到期时间。
task_events 过程日志
  • eventType：例如 task.running、task.completed。
  • summary：人类可读摘要。
  • payload：执行器、工作目录、stdout/stderr 摘要来源、文件改动。
  • 现在开始携带 startedAt、completedAt、durationMs。
task_artifacts 可信产物
  • 第一版只记录文件产物。
  • 附件展示优先从这里生成。
  • 打开文件和“所在文件夹”优先用这里校验。
  • 事件载荷推断只作为兼容兜底。
sessions 任务会话
  • 每个结果产出任务会创建独立任务会话。
  • 通过 parentSessionId 关联回主聊天。
  • 方便未来做任务内上下文、回放和子任务拆解。

执行与协调

第四阶段之前，自动启动、手动启动、进度广播和完成回流比较分散。现在主路径已经收敛到协调器。

TaskService 负责核心任务动作

创建、取消、删除、修改、查询任务，并在后台启动前调用 transitionStatus() 抢占运行权。

createTaskFromChat runTaskInBackground cancelTaskFromConsole deleteSettledTaskFromConsole
TaskExecutionCoordinator 负责执行主路径

自动启动和手动启动都从这里走。它统一处理进度广播、终态消息、桌宠活动、产物收集和恢复空闲。

startTaskInBackground broadcastTaskChanged collectFileArtifacts broadcastPetActivity
TaskRunner 负责真正执行

开发测试走确定性 runner。真实执行走 MultiCliTaskRunner，按优先级选择 Codex、Claude Code 或 Hermes。

registerIpc 负责主进程通信

处理聊天发送、任务取消/删除、打开结果文件、获取详情等 IPC。它不再直接拼完成回流逻辑。

可观测性

第四阶段新增的重点是让用户和开发者知道任务卡在哪、失败在哪、产出了什么。

入口
任务便签增加“详情”按钮

控制台右侧便签可以打开当前任务详情，不必去翻数据库或日志。

数据
task:get-detail 返回聚合视图

主进程将任务、事件、产物整理成 TaskDetail，渲染层只负责展示。

内容
详情展示关键字段

包括状态、执行器、工作目录、安全模式、耗时、产物清单、最近错误和事件时间线。

安全
stdout/stderr 只展示摘要

详情面板不会直接塞完整标准输出和错误流，只展示字节数等摘要信息。

剩余问题

当前已经修稳了地基，但还不是完整的后台作业系统。

队列 还没有完整队列

现在只保证同一个任务不会重复启动，还没有全局并发上限、排队序号和暂停恢复。

控制 自然语言控制仍偏规则化

已支持继续、重试、重新运行、打开结果和删除已完成任务；候选歧义的自然反问还需要补。

提醒 提醒仍依赖应用运行

已支持绝对时间、稍后提醒、编辑 dueAt 和错过提醒文案，但还不是系统级离线调度。

产物 产物类型还少

第一版只处理文件。URL、长文本、日志产物和交付物分级还需要后续补。

优化优先级

按照当前计划，前六阶段已经完成第一版。下一步应补队列、候选反问、重复提醒和系统级离线调度。

阶段 目标 当前状态
第一阶段 状态与启动路径收口 已完成：状态机、原子抢占、防重复启动、手动启动后台化。
第二阶段 抽出任务执行协调器 已完成：自动启动和手动启动统一走 TaskExecutionCoordinator。
第三阶段 结构化任务产物 已完成第一版：文件产物写入 task_artifacts。
第四阶段 任务详情和可观测性 已完成第一版：详情入口、详情面板、耗时载荷、stdio 摘要。
第五阶段 任务控制增强 已完成第一版：继续、重试、重新运行、打开结果、删除已完成任务；候选任务反问还待接入聊天文案。
第六阶段 提醒与日程增强 已完成第一版：绝对时间、错过提醒文案、稍后提醒、编辑 dueAt；重复提醒和系统级离线调度仍待做。
