# 语音延迟复测脚本 v1

> 交互测试规则：助手回答不要求逐字一致；无论措辞如何，都按固定顺序继续，不临时追问。

## 1. 启动与复测约定

从仓库根目录执行：

```bash
cd frontend
npm run dev -- --debug --lock-memory
```



## 2. 主脚本：顺序多轮对话

### 01｜短问候 · 本次启动首轮

> 你好，你在吗？

观察：是否完整听到短输入；能否直接给出简短、可听的回应。

### 02｜自我介绍 · 短输出

> 请用两句话介绍一下你自己。

观察：首句是否完整，是否在完整长答案生成前就开始播放；介绍内容允许随固定人格变化。

### 03｜固定记忆 · 偏好召回

> 我平时喜欢喝什么咖啡？口味上有什么偏好？

语义检查：固定语料包含“热拿铁、不喜欢过甜的咖啡”。未召回或答错也要记录，不把它当成有效快速回答。不要求模型必定使用某个工具。

### 04｜当前上下文 · 中等长度输入

> 今天下午三点，我打算和同学们去河边散步。我会在1～2点时睡午觉，然后2点起床坐地铁。我会坐5站然后步行前往约好的地点。

语义检查：下午三点、同学、河边、先坐地铁后步行；不创建任务。这轮只测当前对话，不要求写入持久记忆。

### 05｜当前上下文 · 更正

> 哦不对，我们说好的是下午4点集合。那我3点出发去坐地铁。

语义检查：确认3点出发，不继续沿用2点。

### 06｜当前上下文 · 指代追问

> 我和同学说好的几点见面来着？

语义检查：下午四点，先看日志。检查更正后的内容是否真正被使用。

### 07｜较长回答 · 首音与实质内容

> 你来想想看我们散完步有什么好吃的可以吃。告诉我充分的理由。

观察：识别与结束话轮判断、模型生成、语音合成与播放的解释是否合理；分别记录开场确认和真正开始解释的时刻，以及播放中的明显长空白。

### 08｜句中停顿 · 不完整输入续说

先读：

> 如果我们需要在30分钟内吃完，

**停顿约一秒**，继续读，不等待助手：

> 你觉得我们去吃什么比较好。

观察：是否在前半句就抢答、漏掉后半句或生成两轮回答。记录实际停顿是否明显偏离约定。延迟从后半句说完开始计算；抢答单记失败，不计成负延迟或“更快”。

### 09｜Task 状态 · 只读询问

> 好的，听你的。现在有没有正在进行的任务？请只告诉我状态，不要创建、恢复或取消任何任务。

语义检查：与本遍开始记录的 Task 状态一致，无状态变更。允许使用上下文已有状态；本轮不保证触发工具读取。若发生读取，区分读取前的有效确认与实际状态答案。

### 10｜多轮收尾 · 简短总结

> 请用两句话总结我今天下午的安排。

语义检查：仍是下午四点、和阿杰在咖啡店、先看日志再选优化点；不把解释或询问当成已执行的优化工作。






## 3. 独立脚本：播放中打断

**另起一次应用运行**，不接在主脚本后面；保持同样的启动参数和环境。此组结果不并入普通话轮延迟。

### I-01｜制造持续播放

> 请分五点介绍怎样安排一次社团活动。

### I-02｜第一次打断

听见助手说完第一句、**下一句已开始且仍在播放时**，立即朗读：

> 先停一下，不用展开了，请只说最重要的一点。

观察：旧语音是否及时停止，新输入是否完整识别，新回答是否遵从“只说一点”。记录实际打断位置，不以屏幕文字出现作为触发点。

### I-03｜连续改口

I-02 的新回答开始播放后，在它**仍在发声时**立即朗读：

> 等一下，改成只告诉我第一步该做什么。

观察：是否最终回答最新问题，是否漏掉开头、混入旧回答或恢复被取消的播报；查看 `droppedFrames` 是否增长。

如果 I-01 提前结束，或 I-02 太短导致没有在播放中插入，标记该次“未形成有效打断”，不要把它归为打断成功。保留记录并另开一遍补测，不在同一上下文反复尝试。

## 4. 计时与日志口径

### 用户实际等待

建议用同一录制时间线同时记录人声和设备输出；使用耳机时需确认录制确实包含系统音频。应用 Debug **不保存原始音频**。没有可回放录音时，可记人工估时，但必须标注“估测”，不能宣称毫秒级改善。

| 指标 | 起止点 |
| --- | --- |
| 首音等待 | 用户最后一个字结束 → 属于本轮回复的第一段可听语音开始 |
| 实质答案等待 | 用户说完 → 首段真正回答问题的内容开始；“好的，我看一下”不算实质状态答案 |
| 打断停播等待 | 插话开始 → 旧回答停止发声；仅用于独立打断组 |

问候或明确要求“简短确认”的轮次，确认本身就是实质答案。记录首句原文，便于核查是否只是用空泛开场换取更早首音。没有有效答案时记失败或未完成，不拿开场白替代。

### 定位瓶颈

在 Live Debug 中用识别文字和轮次顺序定位输入，再结合 `segmentId`、`inputId`、`invokeId`、`sayId`、`clauseId` 及 Profile/generation 关联事件。不要把多个 PREPARE/RESPOND 调用或旧播放片段混成一次响应。

| 阶段 | 重点查看 |
| --- | --- |
| 输入与话轮结束 | 输入 `silence`，STT `sentence_end`、`finish_ended.elapsedMs`，EOU `complete` / `incomplete` / `fallback` |
| 模型与首句 | `provider.request_started`、`first_chunk`、`first_tool_delta`、`say.first_text`、`say.clause_ready`、`say.authorized`，以及 `modelName`、`flushReason` |
| 合成与设备交付 | TTS `queued` / `first_audio`，前端 `devicePlayback.physical.started` / `devicePlayback.physical.completed` |
| 完成与异常 | `history.write.completed`、`renderer.ack.sent`、后端 accepted、错误与丢帧记录 |

注意：

- `silence` 是系统判定的静音事件，不是人声最后一个字的精确结束点；`sentence_end` 也不等于 EOU 最终结束话轮。
- 后端发送音频不等于设备出声。`devicePlayback.physical.started` 根据输出设备时钟观测，仍应结合真实听感或录音检查。
- 优先使用已有阶段 `elapsedMs`，并核对计时起点。SAY 的 `elapsedMs` 从 Harness 消费流开始；TTS 首包耗时不是完整首音等待。
- 不跨前后端进程直接相减时间戳，也不使用 Debug 列表收到事件的时刻计时；后端事件经约 500ms 轮询合并。日志用于归因，统一录制时间线用于端到端测量。
- 事件缺失、截断、丢弃或日志写入失败，标记“观测不完整”，不能据此判断成功。

## 5. 最小记录与比较

每遍记录：脚本版本、日期、代码 commit/未提交改动说明、实验变量、遍次、Profile/Soul 版本、模型及语音配置、设备/网络、Task 初始状态，以及 `launch.options` 中的 `debug`、`lockMemory`、`memoryFixture`。不得记录密钥。

每轮使用以下表头，延迟统一以毫秒填写；无数据填“未测”，失败注明原因：

| 轮次 | 识别/语义是否正确 | 首句原文 | 首音等待 | 实质答案等待 | 打断停播等待 | 异常与日志关联 ID |
| --- | --- | --- | --- | --- | --- | --- |

每遍结束后，从“打开日志目录”复制 `live-debug.jsonl` 及存在的 `.1`、`.2`，同时保存需要的 `speech-diagnostics.log` 及备份和录音。JSONL 会滚动覆盖（每份 5 MiB，最多三份），不要等多轮实验全部结束才归档。关闭 Debug 窗口不会停止采集；清空 Debug 日志不会清除对话 Context，也不会清理 `speech-diagnostics.log`。

比较规则：

- 按相同轮次比较各版本的成功样本中位数、范围及成功数/尝试数；三遍只用于初筛，不宣称统计显著，也不计算不稳定的 P95。
- 第 01 轮启动首轮、02—10 多轮对话、独立打断组分开看。不将不同输入或失败样本揉成一个“平均延迟”。
- 改善应体现为首音或实质答案等待减少，且未以更多抢答、漏识别、错误答案、任务误操作或打断失败为代价。若只是确认更早、实质答案不变，明确写为“确认提前”。
- 慢样本保留并解释；环境变化、脚本误读和无效打断单列，不能静默删掉。结果波动明显时增加完整遍数再下结论。

## 6. 依据与范围

- [开发启动](../../README.md)、[Live 语音 Debug](../live-voice-debug.md)：启动参数、固定记忆、日志及指标边界。
- [固定语料](../../backend/memory/fixtures/benchmark-memory-v1.json)：咖啡偏好、阿杰及项目背景。
- [语音处理](../../backend/main_agent/speech.py)、[Runtime](../../backend/main_agent/runtime.py)、[前端播放](../../frontend/src/main-agent-realtime/client.ts)：VAD/EOU、STT 收尾、模型准入和设备播放观测。

本版优先覆盖无外部副作用的对话，不创建、恢复、取消真实任务，也不查询网络或修改代码。真实任务读取耗时、恢复任务拒绝场景、长时间压力和扬声器回声可另建带固定任务夹具的专项脚本，避免污染这份日常延迟基线。后续若改动朗读文本、轮次或停顿规则，升级脚本版本，不与 v1 直接混算。
