# AuraBot UI Polish + Notifications Stage 3 Spec

## 1. 目标

本阶段承接已经完成的 `A1 UI 产品化`，但重点不再是确定 AuraBot 的产品气质，而是把当前还残留的“半成品感”收干净，并补上真正可用的系统通知主链路。

这一阶段的目标有三件事：

1. 继续把全局 UI 收口到统一的 A1 语言，而不是停在“主要界面差不多了”
2. 把控制台中不属于日常使用层的调试能力移出主界面
3. 把主动提醒和时间提醒接到真实可用的系统通知 MVP

一句话总结：

**把 AuraBot 从“已经有 A1 方向的产品壳”推进到“日常界面更完整、深层调试更收敛、提醒真正能走系统通知”的阶段。**

## 2. 阶段定位

在当前路线里，这一阶段位于：

1. 设置页收口
2. UI 产品化
3. 全局 UI 收口 + 系统通知 MVP
4. 桌宠状态机

其中第 3 阶段不是推翻第 2 阶段，而是对第 2 阶段做两种补齐：

1. 把还不够像 A1 的界面局部继续收紧
2. 把通知从“只有设置承接面和桌宠气泡通道”推进到“App 运行中可用的系统通知”

## 3. 核心设计结论

本阶段锁定以下产品判断：

1. AuraBot 的日常主界面继续坚持 A1：桌宠主舞台第一、聊天室第二、设置中心第三。
2. `Memory Debug` 不再常驻控制台正文，也不放在控制台快捷设置首层。
3. `Memory Debug` 进入完整设置中的独立页，属于深层设置能力。
4. 系统通知先做 `App 运行中` 的 MVP，不做 `App 未运行` 时的离线提醒或系统级调度。
5. 通知点击后的默认回流行为是：**优先聚焦控制台；如果控制台未打开，则打开控制台**。

第 5 条是本 spec 的默认假设。

原因：

- 通知对应的内容大多需要继续对话、查看上下文或调整任务
- 控制台是当前最完整的对话与任务承接面
- 直接只聚焦桌宠会让通知点击后的下一步能力太弱

## 4. 范围

### 4.1 In Scope

本阶段包含：

1. 桌宠悬浮控件、聊天浮层、控制台、设置菜单的视觉余量收口
2. 控制台内存调试入口重构
3. 完整设置中的独立 `记忆调试` 页
4. App 运行中系统通知投递
5. `follow_up / time_reminder / idle_nudge` 三类提醒与系统通知联动
6. 通知开关、权限展示、点击通知后的回流路径
7. 与本阶段直接相关的 e2e、文案和状态文档更新

### 4.2 Out of Scope

本阶段明确不做：

1. App 未运行时的离线提醒
2. 开机自启和后台常驻服务
3. 复杂通知编排器
4. 系统通知里的多按钮交互
5. 桌宠复杂状态机
6. Live2D 表情/动作资源编排台

## 5. 信息架构调整

### 5.1 控制台层

控制台继续保留：

1. 主对话
2. 右侧轻便签
3. 顶部快捷设置入口

控制台移除：

1. 常驻 `Memory Debug` 面板

这意味着控制台更纯粹地承担：

- 聊天
- 任务附属信息
- 最小日常快捷设置

而不再承担：

- 深层调试台

### 5.2 控制台设置菜单层

控制台右上角设置菜单保持“日常常用层”定位。

它只保留：

1. 打开完整设置
2. 语言切换
3. 点击穿透等轻设置

它不承载：

1. 记忆调试
2. 模型深层配置
3. 开发者向诊断能力

### 5.3 完整设置层

完整设置新增一个独立页：

1. `记忆调试`

完整设置页签变成：

1. `通用`
2. `桌宠行为`
3. `模型`
4. `人格`
5. `Live2D 模型`
6. `通知`
7. `记忆调试`

这是本阶段唯一的信息架构扩展。

它的原则是：

- 不把深层调试丢在控制台首层
- 也不把它藏进模型页底部的一个折叠块
- 让完整设置明确区分“日常设置页”和“深层系统页”

## 6. Memory Debug 页规范

### 6.1 页面定位

`记忆调试` 是一个完整设置中的深层页，不是面向日常用户的首要入口。

它的职责是：

1. 查看当前 memory graph 快照
2. 查看 recent events
3. 查看 last recall trace
4. 手动刷新调试快照

它不承担：

1. 记忆系统参数编辑
2. 记忆节点人工 CRUD
3. 复杂可视化图谱编辑器

### 6.2 页面风格

这个页面虽然属于调试页，但仍然要属于 A1 产品系统。

要求：

1. 不做成传统黑底/终端式 debug 面板
2. 仍然沿用纸卡、暖白、圆角的 A1 材质
3. 通过信息分层体现“深层”，而不是靠工程化审美区隔

### 6.3 页面结构

建议结构：

1. 页头 lead
2. 顶部调试工具条
3. metrics 摘要
4. recall trace 区块
5. nodes / edges / recent events 三列或两列内容区

这页仍可以复用现有 `MemoryDebugPanel` 的内容块，但承载位置和壳层应更像完整设置页面。

## 7. 系统通知 MVP

### 7.1 功能目标

系统通知 MVP 只覆盖：

1. `memory.follow_up`
2. `task.time_reminder`
3. `proactive.idle_nudge`

其中：

- 桌宠气泡通道仍然保留
- 系统通知是新增的第二条投递通道

也就是说，这一阶段不是“用系统通知替代桌宠气泡”，而是：

**桌宠气泡继续做陪伴型在场表达，系统通知负责用户不在当前焦点时的补充触达。**

### 7.2 触发条件

系统通知必须同时满足：

1. 对应通知总开关开启
2. 对应子类型开关开启
3. 当前环境支持系统通知
4. 当前 trigger 通过打扰判断

当前三类触发对应关系：

1. `follow_up` → `followUpNotificationsEnabled`
2. `time_reminder` → `timeReminderNotificationsEnabled`
3. `idle_nudge` → `idleNudgeNotificationsEnabled`

### 7.3 不做的事情

这一阶段不做：

1. 通知去重中心
2. 多设备同步
3. App 未运行时调度
4. 通知 action button
5. 通知历史中心

## 8. 通知投递与回流行为

### 8.1 通知内容

系统通知内容继续复用 Aura 的 companion-first 文案方向。

原则：

1. 不要变成系统广播腔
2. 仍像 Aura 在轻轻提醒你
3. 标题和正文都保持短

建议结构：

1. 标题：短、像人在叫你看一眼
2. 正文：保留核心提醒内容

例如：

- 标题：`Aura 想提醒你一下`
- 正文：`你前面记下的那件火锅的事，我到点来叫你了。`

这类具体措辞不是硬模板，但语气方向要稳定。

### 8.2 通知点击

通知点击后的默认行为：

1. 如果控制台已打开：聚焦控制台
2. 如果控制台未打开：打开并聚焦控制台

不区分三类通知的点击行为。

原因：

1. 用户点击通知后大概率想继续处理、追问或修改
2. 当前控制台是最完整的承接面
3. 统一回流路径能减少分支复杂度

### 8.3 不做的点击后行为

这一阶段不做：

1. 按通知类型分别跳不同界面
2. 直接滚到某个记忆节点
3. 直接高亮某个任务详情
4. 打开独立通知中心

## 9. 设置页承接面

### 9.1 通知页

通知页继续是通知配置唯一主承接面。

本阶段在已有基础上要做到：

1. 开关真的能控制系统通知投递
2. 权限状态真的反映当前环境能力
3. 页面文案明确说明当前边界

通知页需要明确说明：

1. 现在只支持 App 运行中的提醒
2. App 没运行时不会主动弹系统通知

这句边界提示非常重要，因为它决定用户预期。

### 9.2 记忆调试页

新增 `记忆调试` 页后，通知页不再承担任何记忆调试内容。

这样信息边界更清晰：

- 通知页回答：什么时候提醒、怎么提醒
- 记忆调试页回答：记忆系统现在内部是什么状态

## 10. UI 收口余量

本阶段 UI 收口的重点不是再做大规模重设计，而是把当前残留的不统一点收干净。

重点区域：

1. 桌宠悬浮控件
2. 桌宠聊天浮层
3. 控制台头部工具条
4. 控制台右侧便签与调试/设置层级
5. 设置菜单
6. 通知页与记忆调试页的统一壳层

统一要求：

1. 保持 A1 材质与色彩
2. 避免工程后台感
3. 避免“视觉上又开了新系统”

## 11. 技术边界

### 11.1 Main Process

新增或补齐的责任大致包括：

1. 系统通知发送器
2. 通知点击后的窗口聚焦行为
3. 通知开关与 trigger 结果之间的连接

### 11.2 Proactive / Reminder Flow

现有 `ProactiveTriggerEngine` 继续是 trigger 中心。

这一阶段不重写 trigger engine，只补：

1. 桌宠气泡之外的系统通知分发
2. 不同通知开关的 gating

### 11.3 Renderer

renderer 继续负责：

1. 设置页可视化承接
2. 记忆调试页承接
3. 相关状态同步展示

renderer 不负责：

1. 决定是否真的发系统通知
2. 系统通知点击后窗口管理

## 12. 风险与防偏移

### 12.1 通知做成系统广播

风险：

- 文案突然脱离 Aura 的人格

避免方式：

- 继续走已有 `VoiceAdapter` / workflow 方向
- 通知内容也遵守 companion-first 语气

### 12.2 调试能力回流到主界面

风险：

- 控制台再次被深层调试能力侵占

避免方式：

- Memory Debug 只留在完整设置独立页
- 控制台首层不再常驻

### 12.3 系统通知范围摊太大

风险：

- 一下子卷入离线调度、开机自启、复杂权限流

避免方式：

- 锁死本阶段是 App 运行中 MVP
- 离线边界只做提示，不做实现

## 13. 推荐实施顺序

建议按下面顺序落：

1. 把 Memory Debug 从控制台正文移出
2. 重做控制台设置菜单为“左侧小栏 + 右侧内容”
3. 在完整设置新增独立 `记忆调试` 页
4. 接系统通知发送器与主进程聚焦逻辑
5. 把通知页开关真正接到 trigger 分发
6. 补 e2e / 状态文档 / 边界说明

原因：

1. 先把信息层级理顺
2. 再接真正的通知能力
3. 最后补验证与边界提示

## 14. 验收标准

本阶段完成时，应满足：

1. 控制台正文不再常驻 Memory Debug
2. 控制台设置菜单只承担日常设置层
3. 完整设置中存在独立 `记忆调试` 页
4. `follow_up / time_reminder / idle_nudge` 在 App 运行中可以走系统通知
5. 点击系统通知会把用户带回 AuraBot 控制台
6. 通知页能真实控制通知投递
7. 文案与 UI 仍然统一属于 A1，而不是突然长出一套系统工具感
