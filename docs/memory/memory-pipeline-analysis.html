记忆系统流水线分析

这份文档从一条用户消息进入 AuraBot 开始，拆开当前记忆系统的判断、抽取、写入、合并、连边、召回、主动提醒和调试路径。它偏工程说明书，但尽量用示例讲清楚每个阶段为什么存在、输入是什么、输出又去了哪里。

当前形态一句话

存储SQLite 本地表：nodes、edges、summaries、event logs。
写入Gate 决策后抽取候选，串行合并和补边。
召回Planner + 本地 scorer 选 seed，再沿图有界扩散。
提醒follow_up 节点到期后通过聊天或后台 scheduler 触发。

1. 总览：它不是一块“记事本”，而是一条受控图记忆流水线

AuraBot 当前记忆系统的核心不是把所有聊天塞进一个长摘要，也不是把文本切 chunk 后做向量搜索。它的主线是：把值得长期使用的信息写成受控类型的 memory_nodes，再用 memory_edges 表达节点之间的关联，后续对话先找到少量入口节点，再沿边扩散到相关记忆。

Gate 先决定要不要写 gateModel 会返回 memoryDecision。只有 write_now 才进入长期记忆写入。
Extractor 只产候选 抽取阶段只给出候选节点和可选前置关系，不直接写数据库。
Service 控制写库 MemoryService 统一处理队列、合并、补边、召回和到期 follow-up。
Debug 解释召回路径 最近一次召回 trace 会记录 seed、expanded、returned 和 traversed edges。

2. 数据模型：节点存信息，边存关系，摘要是辅助视图

当前 schema 定义在 src/shared/schemas/memory.ts 和 src/shared/constants/memory.ts，SQLite 表结构在 src/core/storage/migrations.ts。每条记忆都归属某个 profileId，避免不同用户画像互相污染。

对象 字段重点 它在流水线里的作用
memory_nodes type、state、content、importance、starts_at、ends_at 保存可独立召回的一条事实。类型包括 trait、preference、event、follow_up。
memory_edges source_node_id、target_node_id、relation_type、weight 保存节点间关联。类型包括 relates_to、caused_by、scheduled_for、preference_for、opposes。
memory_summaries topic、content、updated_at 按 topic 保存轻量摘要，目前是 append 式辅助上下文，不是真相源。
event_logs gate.decision、memory.write_completed、memory.recall_used、memory.follow_up_triggered 给 Memory Debug 和开发排查提供可观察轨迹。

3. 写入流水线：从用户消息到稳定节点和关系边

1

用户消息先落库

ChatOrchestrator.sendMessage() 会先创建 user message，并取最近上下文给 gate 使用。

  • 输入：用户当前输入、最近消息。
  • 输出：已持久化的 user message。
  • 好处：即使后续模型失败，用户输入也不会丢。
2

Gate 决定聊天类型和记忆动作

gateModel.evaluate() 返回 replyDecision、inputKind、memoryDecision、coalescedText 等字段。

  • replyDecision = wait：暂不回复，也不写长期记忆。
  • inputKind = task：进入任务系统，跳过记忆写入。
  • memoryDecision = write_now：进入抽取和写入。
3

Extractor 产出候选记忆

生产路径由 memoryModel 结构化抽取；测试或显式 fallback 使用 DeterministicMemoryExtractor。

  • 候选节点包含 type、content、importance、可选 startsAt/endsAt。
  • 同一轮里 follow-up 可带 relationToPrevious，用于连接上一条 event。
4

写入队列串行处理

MemoryWriteQueue 使用 p-queue，并发数为 1。

  • 避免两个写入同时读取旧图、各自补边，造成关系丢失或重复。
  • 每个候选都经过同一套 merge 和 relation 规则。
5

Merge Planner 判断新建还是更新

MemoryMergePlanner 接收 candidate 和已有 nodes。模型路径可做语义合并，确定性路径只做同 type + content 精确匹配。

  • create：继续进入 relation planner。
  • update_existing：更新旧节点 content、importance、时间字段和 updatedAt。
6

Relation Planner 补图边

MemoryRelationPlanner 为新节点和已有节点规划边。模型路径会过滤发明的 node id；确定性路径根据共享概念连边。

  • event / follow_up 与 preference 共享概念时，倾向 preference_for。
  • 其他共享概念默认 relates_to。
  • 同一 source、target、relationType 有唯一约束。
7

Repository 写入 SQLite 和摘要

MemoryRepository.createNodeFromWriteRequest() 负责事务写入 node、summary 和 edge。

  • 新节点默认 state = active。
  • 重复节点只提升 importance 并刷新 updatedAt。
  • summary 目前按 topic append。

4. 召回流水线：先找入口，再沿图走

AuraBot 的召回不是“把所有记忆按时间拼进去”。当前策略是先从用户 query 找到最多 4 个 seed nodes，再用 GraphTraversal 沿边做默认深度 2、最多 8 个扩展节点的有界扩散。

1

读取当前 profile 的非归档上下文

getMemoryContext(profileId) 取出所有 state != archived 的 nodes、edges 和 summaries。

  • 节点按 importance 和 updatedAt 排序。
  • 当前 completed follow_up 仍会出现在普通上下文中，但到期扫描只看 active follow_up。
2

Recall Planner 生成语义计划

模型路径返回 queryTerms、targetTypes、rankedNodeIds。确定性路径返回空计划。

  • queryTerms 会并入本地 scorer。
  • rankedNodeIds 必须来自已有节点，发明 id 会被过滤。
3

本地 scorer 选择 seed nodes

scorer 综合文本命中、概念命中、类型偏权、targetTypes 和 importance。

  • “喜欢/讨厌/吃什么”偏向 preference。
  • “明天/下周/安排/别忘”偏向 event。
  • “提醒/记得/跟进”偏向 follow_up。
4

沿边扩散并记录 trace

collectRelatedMemoryTrace() 默认双向看边，按累计边权排序，跳过已访问节点和超过深度的候选。

  • 返回 nodes、summaries 和 trace。
  • trace 包含 seedNodeIds、expandedNodeIds、returnedNodeIds、traversedEdges。

5. Follow-up 流水线：提醒是特殊记忆节点，不只是任务

在记忆系统里，follow_up 是一种节点。它和普通偏好/事件一样能参与召回，但它额外使用 startsAt 表示触发时间。

  • 主聊天路径：每次回复前调用 retrieveDueFollowUps()，把到期提醒放进回复上下文。
  • 后台路径：MemoryFollowUpScheduler 每 60 秒轮询，发现到期后推送桌宠气泡。
  • 完成后：调用 completeFollowUps() 把节点状态改为 completed，避免重复提醒。
if node.type === "follow_up"
and node.state === "active"
and node.startsAt <= now:
  render memory.follow_up
  broadcast pet activity
  update state -> completed
  record memory.follow_up_triggered

6. 完整示例：火锅、阿杰和提醒如何穿过整条流水线

第 1 轮

用户说偏好

“我喜欢吃火锅。”

candidate:
  type: preference
  content: 用户喜欢火锅
  importance: 0.72
第 2 轮

用户说事件和提醒

“我明天要和阿杰去吃火锅，提醒我别忘了。”

candidate A:
  type: event
  content: 用户提到一个时间相关事件...

candidate B:
  type: follow_up
  relationToPrevious:
    scheduled_for: event
第 3 轮

用户问相关事项

“阿杰那件事我该顺便注意什么？”

seed:
  event: 和阿杰去吃火锅

expanded:
  preference: 用户喜欢火锅

图上的结果

preference 用户喜欢火锅
←
event 用户明天要和阿杰去吃火锅
←
follow_up 需要跟进或提醒用户：明天别忘

这就是当前图记忆的核心价值：第 3 轮问题没有直接说“火锅偏好”，但 query 先命中阿杰相关 event，随后沿 preference_for 边扩散到“用户喜欢火锅”，回复就能同时理解事件和稳定偏好。

7. 调试与验证：怎么知道它为什么记住、为什么召回

Memory Debug 面板

设置里的 Memory Debug 会展示节点数、边数、摘要数、最近 memory event，以及最近一次召回 trace。trace 最适合排查 “为什么没有召回”或“为什么召回了不相关内容”。

  • seedNodeIds：入口节点是否选对。
  • expandedNodeIds：图扩散是否走到了相关节点。
  • traversedEdges：边类型、权重和深度是否合理。
  • recallPlan.queryTerms：模型或 planner 是否给了有用语义词。

固定评估

corepack pnpm eval:memory 会跑 tests/fixtures/memory/recall-evaluation.json。

  • preference-direct-keyword：偏好问题能直接召回。
  • event-to-preference-graph-hop：事件 query 能沿边跳到偏好。
  • follow-up-due-filter：提醒召回能排除不相关未来 follow-up。

8. 当前边界和下一步

边界 现在的状态 后续改进方向
语义检索 没有 embedding、BM25 或实体索引，主要靠 planner terms + 本地 scorer。 引入混合检索作为 seed node 选择器，图扩散仍负责解释。
来源追溯 写入请求有 sourceSessionId，但节点和边还没有完整 episode provenance。 新增 memory_episodes，让节点和边都能追溯到原始消息或任务结果。
边模型 边只有 relationType、weight、createdAt，没有 state、confidence、validFrom/validTo。 把边升级为可维护事实，支持失效、降权和时间窗口。
摘要层 memory_summaries 当前按 topic append，无法精确重建。 让摘要成为可重建视图，而不是真相源。
用户控制 已有 debug 展示，但还没有完整的节点/边审阅、编辑、删除和 forget 工作流。 补记忆审阅 UI 和同步处理节点、边、摘要、未来索引的遗忘流程。

这套系统现在最值得保护的是“受控”和“可解释”：模型可以帮助抽取、合并、补边和重排，但最终写库必须继续由 schema、service 和 repository 收口。
